# TYT UVL-15W Update Protocol V1.0

Status: reverse-engineered from the official TYT CPS build dated 2026-07-23 and
successful physical-Radio captures. This specification is authoritative for
this repository's updater implementation, subject to the evidence limits below.

## 1. Scope and evidence status

This protocol is separate from normal Codeplug cloning. It covers:

- MCU Firmware Update from an official `.Fir` package;
- Resource Flash from a TYT address-record `.DAT` package;
- Language Resource Write, which is a Resource Flash operation.

It does not cover Bluetooth firmware, arbitrary/custom firmware, activation
material, or the boot-picture PNG workflow.

Evidence labels used below:

- **Captured**: observed in a successful official-CPS physical-Radio session.
- **Reproduced**: independently regenerated byte-for-byte from retained files.
- **Structure confirmed**: proven from vendor packages, without a corresponding
  physical write capture.
- **Unresolved**: insufficient evidence for a safe implementation.

| Operation                              | Status                                   |
| -------------------------------------- | ---------------------------------------- |
| Firmware `3.7.23` package and transfer | Captured twice; fully reproduced offline |
| Language `1.01.05` Resource Flash      | Captured repeatedly bidirectionally      |
| Image `1.01.00` Resource Flash         | Captured fresh and during recovery       |
| Combined language/image Resource Flash | Captured once bidirectionally            |

Language-only, Image-only, and combined Resource Flash are physically captured.
The official CPS's variable `E3` source has also been explained by static binary
analysis. All four exact packages have completed the browser success path on
one compatible Radio and are released as beta; stable promotion remains gated
as described in section 11.

## 2. Transport and frame envelope

The observed official updater opens a USB CDC serial port at `115200 8N1`, no
flow control, and changes RTS from false to true after opening. All traffic uses
the same envelope, byte escaping, and LRC rules as the reviewed clone protocol:

```text
request:  FE... FE EE EF CMD escaped(payload) escaped(LRC) FD
response: FE... FE EF EE CMD escaped(payload) escaped(LRC) FD
```

The updater must consume a continuous byte stream, tolerate arbitrary transport
chunk boundaries, validate LRC before interpreting a frame, and advance only on
the exact expected response. Timing observations from the captures are not
protocol timeouts.

All update communication is local browser-to-Radio communication. No package,
identifier, session key, or serial traffic is sent to an application server.

## 3. Shared update-mode handshake

Both protocol families use this captured sequence before data transfer:

1. The update-mode Radio emits one or more unsolicited `9C` responses with
   payload `00`.
2. Host sends `C0 00`; Radio responds `0C` with `00 + "OK"`.
3. Host sends seven `C1` requests for indexes `00..06`. Each payload is
   `[index, HH, MM, SS]`, with local time encoded as packed BCD.
4. Radio responds to each with `1C`, echoing the index followed by its field.

Observed response fields include hardware/bootloader data, build information,
model, firmware version, build timestamp, and opaque identity/activation data.
Opaque fields are protocol inputs only: never display, persist, or log their raw
values.

After a successful transfer, the host repeats `C0` and all seven `C1` exchanges,
then sends `C4 00`. The Radio responds `4C` with `00 + "OK"`.

The implementation must match each `1C` response to its requested index and
must not assume response arrival aligns with transport read calls.

## 4. Firmware package validation

An accepted `.Fir` package is binary. For the captured `3.7.23` package:

- bytes `0x00..0x0F` are its integrity tag;
- bytes from `0x10` onward are the body transformed and transmitted in blocks;
- bytes `0x10..0x13` are also used by final Radio verification.

Validate before opening the serial port:

1. Encode `.Fir[0x10:]` as uppercase hexadecimal ASCII.
2. Compute MD5 of that ASCII byte sequence.
3. Encrypt the 16-byte digest with the modified XXTEA routine below, using the
   first 16 bytes of this official-CPS constant as the key:

   ```text
   178B09AA043DFF60370D542FCA9C30AA
   ```

4. Require the encrypted digest to equal `.Fir[0x00..0x0F]` exactly.

The MD5 is part of the vendor format and is not a claim of modern signature
security. This check proves package consistency with the official CPS; it does
not authorize arbitrary firmware or establish a public-key chain of trust.

### Modified XXTEA

- Input length is a multiple of four bytes and at least eight bytes.
- Interpret input and 16-byte key as little-endian unsigned 32-bit words.
- Use the standard corrected Block TEA/XXTEA mixing expression.
- Use delta `0x645A75C5` instead of the common XXTEA delta.
- Use `32 + floor(52 / wordCount)` encryption rounds.
- All arithmetic wraps modulo `2^32`.

The repository evidence verifier is the executable regression oracle for this
description.

## 5. Firmware session key

The 16-byte per-session block-transform key is derived from the initial shared
handshake:

1. Take the 12 data bytes after the index in `1C` response index `00`.
2. Parse the ASCII bootloader build timestamp from `1C` response index `02`.
3. Replace byte 5 of the 12-byte value with the final ASCII character of that
   timestamp.
4. Replace byte 9 with the timestamp minute tens ASCII character.
5. Replace byte 11 with the timestamp minute units ASCII character.
6. Append `5D`.
7. Append the exact three packed-BCD time bytes sent in the first `C1` request.

The resulting key is 16 bytes. It is transient sensitive data: keep it only for
the active update, zero/release it afterward where practical, and never log it.
Two independent captures were reproduced in full with independently derived
keys.

## 6. Firmware transfer state machine

After package validation and the shared handshake:

1. Split `.Fir[0x10:]` into 512-byte blocks; the final block may be shorter but
   remains a multiple of four for the captured package.
2. Encrypt each block independently with modified XXTEA and the session key.
3. Send `C2` with payload:

   ```text
   totalBlocks BE16 | blockNumber BE16 | dataLength BE16 | encryptedData
   ```

   Block numbers are one-based.

4. Wait for `2C "OK"` before sending the next block. Because the acknowledgement
   does not echo a block number, the host must own strict sequence state and
   reject duplicate, missing, late, or unexpected acknowledgements.
5. After the final acknowledgement, send `C3 HH MM SS`, using current local time
   as three packed-BCD bytes.
6. Require `3C` payload to equal `.Fir[0x10..0x13]` repeated twice.
7. Perform the shared post-transfer handshake and `C4` completion.

Captured `3.7.23` transfer facts:

- 1,590 `C2` blocks;
- blocks 1 through 1,589 contain 512 bytes;
- block 1,590 contains 464 bytes;
- all 1,590 request/acknowledgement pairs strictly alternate.

Do not send the package body untransformed. Do not report success on receipt of
an arbitrary `3C`; compare the exact expected verification value and then
verify the installed version after reboot in normal mode.

## 7. Resource Flash package and transfer

### DAT grammar

Every validated record is one ASCII line:

```text
AAAAAAAA0020<64 uppercase hexadecimal data characters>\n
```

- `AAAAAAAA`: absolute hexadecimal address text;
- `0020`: fixed 32-byte record length;
- final 64 characters: the 32 data bytes.

Reject malformed hex, wrong length, duplicate addresses, non-increasing or
non-contiguous records, overlapping records, and addresses outside an
operation-specific allowlist before opening the serial port.

Validated package facts:

| Package            | Records | Decoded address range    |
| ------------------ | ------: | ------------------------ |
| Language `1.01.05` |   3,089 | `0x00740000..0x00758220` |
| Image `1.01.00`    |  92,717 | `0x00170000..0x004445A0` |
| Combined latest    | 208,896 | `0x00170000..0x007D0000` |

The upper bound is exclusive. Every record from the separate language and
image packages matches the record at the same address in the latest combined
package. Thus both language and image resources are present in that combined
flash image (**Structure confirmed**).

### Captured language and image transfers

After the shared handshake:

1. Host sends `E3` with the eight-byte compatibility payload described below.
2. Radio responds `E3 "WRITE START OK"`.
3. Host sends `E4` blocks with payload:

   ```text
   address BE32 | declaredLength BE16 | data
   ```

4. After every block, require `E6` payload:

   ```text
   "WF OK" | echoedAddress BE32 | echoedDeclaredLength BE16
   ```

If the Radio returns `EE / Frame Head Error`, `Frame Tail Error`,
`Frame Length Error`, or `Frame Lrc Error`, resend the exact same encoded `E4`
frame at most two additional times. These responses mean the Radio rejected the
frame before executing its Resource Flash request. Do not rebuild the payload,
change the address, or advance the block counter until the matching `E6`
acknowledgement arrives. `Option Value Error`, other responses, timeouts,
disconnects, and exhausted retries are not automatically retried and enter
Update Outcome Unknown after writing has started.

The additional parser-error retry policy is supported by the reviewed protocol
error definitions and the 2026-08-28 browser trace at block 2,218: the Radio
returned `Frame Head Error` for address `0x00285200`, while the browser's
525-byte frame had valid framing/LRC and matched the successful official-CPS
frame for that address byte-for-byte.

5. Host sends `E5 "Read Complete"`; Radio responds `E5 "OK"`.
6. Perform the shared post-transfer handshake and `C4` completion.

For Language `1.01.05`, the official CPS expands 3,089 32-byte DAT records into
193 512-byte blocks plus one final 32-byte block. The final `E4` nevertheless
declares 512, and its `E6` response echoes 512. The 98,848 transmitted data bytes
match the DAT exactly.

For Image `1.01.00`, the official CPS expands 92,717 records into 5,794
512-byte blocks plus one final 416-byte block. The final block again declares 512. All 2,966,944 transmitted bytes and all 5,795 acknowledgements match the
package exactly.

For the combined Language `1.01.05` and Image `1.01.00` package, the official
CPS expands 208,896 records into 13,056 full 512-byte blocks. All 6,684,672
transmitted bytes and acknowledgements match the package exactly.

The observed completion string is literally `"Read Complete"`, despite this
being a write. Implement the captured value, not the normal Codeplug write
completion string.

### E3 construction and compatibility policy

Seven observations contain six different successful `E3` payloads. Static
analysis of official CPS SHA-256
`6677766dee106cf143861b888a2c5322d5279af216a32817c8a699f356f59590`
shows the exact builder at virtual address `0x140056670`:

1. select the ASCII frame prefix `FE FE EE EF E3`;
2. read 32-bit words at updater-object offsets `+0x54` and `+0x58`;
3. render each word as eight zero-padded hexadecimal characters;
4. concatenate and frame-decode those 16 hexadecimal characters as eight
   payload bytes.

Those offsets lie inside a 24-byte managed value beginning at `+0x48`; the same
binary constructs and destroys values at `+0x48`, `+0x60`, `+0x78`, and so on
in 24-byte strides. Identifying it more narrowly as a Qt/C++ value is an
inference; the overlap, stride, field reads, and formatting behavior are pinned
static facts. The two words are incidental object representation, not a value
derived from the DAT, its address range, the Radio handshake, or time. The
captured variation—including `C42FC32FC62FC52F`—and successful `WRITE START OK`
responses are consistent with that binary behavior.

Do not reproduce Qt object-layout leakage in the browser. Use the exact
known-successful compatibility payload for the validated package kind:

| Package kind | Mode     | E3 payload         | Evidence                                |
| ------------ | -------- | ------------------ | --------------------------------------- |
| Language     | Fresh    | `0000000D00000000` | Two complete writes, captures 03 and 09 |
| Image        | Fresh    | `0000001D00000000` | Complete 5,795-block write, capture 06  |
| Image        | Recovery | `0000000000000000` | Full partial-state recovery, capture 10 |
| Combined     | Fresh    | `0000001100000000` | Complete 13,056-block write, capture 07 |

This is a version-scoped compatibility policy, not a universal protocol
constant. Require the validated package kind and supported model/CPS evidence
set before selecting it. A different package type, model, bootloader, or
protocol revision requires new evidence. Browser release still requires one
physical test of each enabled package kind, but no further official-CPS capture
is required for this build.

## 8. Package compatibility and ordering

The supplied TYT operation instructions require flash data before firmware
versions after `3.5.16`, Language `1.01.04` before versions after `3.7.11`, and
Language `1.01.05` before Firmware `3.7.23`. Treat these as an executable
prerequisite graph, not a dismissible warning.

Before enabling an update, require:

- exact Radio model and validated hardware/bootloader compatibility;
- valid package structure, integrity, type, and hash;
- installed resource/firmware versions sufficient for the requested ordering;
- stable local connection and explicit user confirmation;
- no concurrent Radio operation.

The current evidence does not establish downgrade, cross-model, test-firmware,
or arbitrary-address safety. Those operations remain unsupported.

## 9. Failure and recovery semantics

Never retry a destructive request blindly. A retry is allowed only when its
idempotence and Radio response are established for that exact state.

Before erase/write begins, validation or connection failures are ordinary
failures. After the Radio accepts an update start or any data block, a timeout,
disconnect, browser close, process crash, unexpected response, failed reboot,
or failed post-reboot verification produces **Update Outcome Unknown**.

For that outcome, retain locally:

- operation and package SHA-256;
- non-reversible phase and last acknowledged block/address;
- timestamps and sanitized Radio fingerprint;
- expected versions and safe vendor recovery instructions.

Never retain raw `1C` identity/activation fields or session keys. Never claim
success until final protocol verification, reboot/reconnection, installed
version verification, and a normal Codeplug read all succeed.

### Bounded parser-error block retry

The Radio can reject a structurally valid data frame with `Frame Head Error`,
`Frame Tail Error`, `Frame Length Error`, or `Frame Lrc Error` before executing
the block. For only those explicit parser responses, the browser may resend the
exact same encoded `C2` Firmware block or `E4` Resource Flash block, with three
total attempts. Encryption, payload, block number/address, and declared length
must not be recomputed or advanced between attempts. Progress advances only
after the matching `2C "OK"` or `E6` acknowledgement.

This exception does not authorize retrying `Option Value Error`, unknown or
unexpected responses, timeouts, disconnects, handshake/start commands,
Firmware verification, Resource completion, or finalization. Exhausting the
three attempts remains Update Outcome Unknown and retains the preceding
acknowledged block/address.

### Transfer-timeout diagnostics

A `TX` frame record alone does not prove that the Web Serial writer accepted
the bytes. During `C2` and `E4` transfer loops, the internal diagnostic buffer
therefore records four distinct boundaries: the encoded request, successful
serial-write completion, each raw RX chunk before frame decoding, and the
decoded response. On timeout or connection closure it also records the number
of bytes still buffered by the response decoder, including those bytes only
while transfer-only raw tracing is enabled.

These diagnostics distinguish a rejected frame, a failed serial write, no
response after a completed write, and a truncated response. They do not make a
timeout safe to retry. Raw tracing is disabled during both identity handshakes
and finalization so `1C` identity/activation fields remain excluded.

Protocol events are never rendered as a live frontend console. The newest 120
events remain in memory and are included only when the user explicitly
downloads an error report after an ordinary failure or Update Outcome Unknown.
The JSON report also contains the failure code and phase, package metadata,
progress, recovery state, browser identification, page URL, and recent serial
traffic. That traffic can contain transmitted package blocks. The report does
not contain firmware session keys or `1C` identity/activation payloads, and it
is never uploaded automatically.

The persisted outcome-unknown record includes the validated package summary
without package bytes. This allows the same package metadata to be restored in
the report after a page reload. Older records without the summary remain
readable and retain the existing recovery path.

### Captured Image recovery profile

Capture 10 starts from a known partial Image write after block 418 had been
acknowledged. The official CPS does not resume from block 419. It sends the
recovery-only all-zero `E3` payload, rewrites the entire validated Image
`1.01.00` package from address `0x00170000`, receives all 5,795 acknowledgements,
finalizes, and then performs a normal Radio read.

The browser may use this profile only after a normal-mode Radio inspection and
selection of the exact package hash recorded for the interrupted Image update.
Recovery still starts at the package's first address. Do not substitute the
fresh Image payload, resume from the stored block/address, or apply this profile
to Language, combined, Firmware, another package, or another Radio build. If an
exact recovery profile is absent from the catalog, reject before opening the
serial port and direct the user to the official TYT CPS.

After a successful normal-mode Radio Read, the user may explicitly confirm that
recovery was completed with the exact package in the official CPS. This clears
only the browser's persisted outcome-unknown record and performs no Radio
write. The record must not be clearable through this path before the normal
read succeeds.

## 11. Browser implementation and release gate

Release-specific data is owned by
[`data/update-catalog/uvl15w.json`](../../data/update-catalog/uvl15w.json).
The generic package and transport modules consume this catalog; they do not own
firmware versions, package hashes, resource address maps, prerequisites, or
captured update-mode identities. The adjacent catalog README is the required
procedure for adding older or newer packages without widening compatibility by
accident.

The browser implementation follows these boundaries:

- `modules/update-catalog`: versioned package, compatibility, prerequisite, and
  normal-mode firmware support policy loaded from the data catalog;
- `modules/update-package`: exact package classification, SHA-256, Firmware
  integrity, DAT grammar, continuity, and address policy;
- `modules/uvl15w-updater`: update-mode handshake, compatibility policy,
  Firmware and Resource state machines, transforms, acknowledgements,
  finalization, and sanitized recovery facts;
- `components/update-coordinator-controller.tsx`: exclusive operation
  ownership, persistent Update Outcome Unknown records, restart flow,
  installed-version checks, and complete post-reboot Radio Read;
- `components/update-coordinator-provider.tsx`: the small React context seam
  consumed by update screens;
- `components/updates`: the localized single-Radio flow, split into package,
  preparation, transfer, verification, and shared-feedback components.

The preparation screen exposes browser connection readiness before Start can
be enabled. Active updates lock unrelated navigation with an operation-specific
message, and the Codeplug status footer is hidden on the updater route so it
cannot be mistaken for update status.

Each catalog package owns an explicit `disabled`, `beta`, or `stable` release
status. `disabled` packages are rejected before Web Serial. `beta` packages
require a risk dialog on every Updates-page visit and explicit acknowledgement
before package selection. The acknowledged state is passed into the normal
preparation policy and enforced again by the coordinator before writing.
`stable` requires a second compatible Radio and the controlled
interruption/recovery matrix. Follow
[`../testing/updater-manual-validation.md`](../testing/updater-manual-validation.md)
before changing a package's status; never derive availability from build mode,
filename, version, or package kind.
